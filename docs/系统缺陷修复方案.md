# 系统缺陷修复方案

## 1. 文档状态

- 范围：覆盖 2026-08-07 代码与运行状态审计中确认的全部缺陷和条件性风险。
- 交付：拆分为 P0、P1、P2 三个可独立发布的版本，不做一次性大合并。
- 约束：继续使用 Go 标准库和单文件 JSON，不引入数据库或第三方依赖。
- 依据：[领域词汇表](../CONTEXT.md) 与 [ADR](adr/) 中已经确认的业务语义和边界。

## 2. 已确认的关键决策

1. 验证码查询是幂等读取。有效期内所有授权请求都返回当前最新验证码，不存在领取、消费或 ACK。
2. 公开匿名注册在管理员初始化后永久关闭；普通用户只能由管理员创建。
3. 保留 JSON 存储，但所有变更采用“修改副本、成功落盘、再发布内存状态”的事务式提交。
4. IMAP 游标表示连续完成检查的位置，并与 `UIDVALIDITY` 绑定；世代变化时回看最近 24 小时。
5. 面板取码使用同源 Web Session，外部 API 才使用邮箱 token 和 `public_base_url`。
6. 删除用户前先阻止新操作并等待后台工作退出；30 秒超时返回 `409 user_busy`，不强制删除。
7. 在线更新没有可信 SHA-256 时只能提示，不能替换可执行文件。

## 3. 修复目标与非目标

### 3.1 目标

- 邮件积压、邮箱世代变化和服务重启均不造成游标跨越或永久漏信。
- 一封邮件只依据结构化收件人地址归属到正确邮箱。
- Apple 2FA 流程严格归属于发起它的面板用户，不能跨用户提交或并发重放。
- 任何返回失败的持久化操作都不会改变进程内可见状态。
- 匿名请求不能抢注管理员、无限注册用户或用密码计算阻塞全局 Store。
- 现有验证码外部 API 保持兼容，并改为可重复读取新鲜验证码。
- 后台任务、用户删除、服务关闭和凭据更新具有确定的生命周期。
- 前端对失败、忙碌、分页和反代部署给出正确行为。

### 3.2 非目标

- 不迁移 SQLite，不支持多实例共享写入。
- 不改变 Apple/iCloud 第三方协议本身。
- 不引入验证码领取租约、消费标记或客户端 ACK。
- 不全量回扫历史收件箱；`UIDVALIDITY` 变化默认只回看 24 小时。
- 不在本轮重新设计页面视觉样式。

## 4. 当前基线

- 当前状态文件约 3.54 MiB，包含 1 个用户、6 个账号、4010 个邮箱、350 封缓存邮件和 6 个 iCloud 会话。
- 数据完整性检查未发现重复 ID、重复邮箱、孤儿引用或非法邮箱状态。
- 当前配置端口为 `50001`，审计时没有监听进程；全局 API Key 未配置，因此自动取号和批量查询 API 不可用。
- `go test ./... -count=1`、`go vet ./...`、`go build ./...` 通过；语句覆盖率为 59.1%。
- 当前环境未能运行 race detector：`CGO_ENABLED=0` 且没有 C 编译器。

## 6. P0：正确性与安全边界

### P0-01 事务式 JSON 状态提交

**现状与根因**

`internal/app/store.go` 的写方法普遍先修改 `s.state`，最后调用 `saveLocked`。磁盘满、目录不可写或 rename 失败时，调用者收到错误，但变更已经留在内存；后续任意成功保存还会把这次失败变更带入磁盘。注销接口又忽略删除会话的错误，重启后旧 token 可能重新有效。每条消息和每个游标还会各自重写完整 JSON。

**修复设计**

- 新增 Store 内部唯一写入口，语义固定为：
  1. 在锁内克隆当前 `State`。
  2. 对克隆状态执行校验和修改。
  3. 将克隆状态写入同目录临时文件，完成 flush/close 后原子替换正式文件。
  4. 只有替换成功才把 `s.state` 指向新状态。
- 任何失败都丢弃副本，旧内存状态和旧磁盘文件保持不变。
- 临时文件必须使用唯一名称、权限 `0600`，失败后清理；替换失败时不得删除旧正式文件。
- 将一次 IMAP 同步中的消息 upsert、邮箱游标、账号游标合并为一个 Store 提交，避免一次批次重写几十次 3.54 MiB 文件。
- 所有 Store 写入口验证 `owner_id`、`account_id`、`mailbox_id` 的存在和归属；管理员删除完成后，旧任务无法写入孤儿数据。
- 密码哈希、Apple/IMAP 网络请求和其他慢操作全部放在 Store 锁外。
- 登录成功时的 `LastLoginAt` 与 WebSession 创建合并提交；管理员初始化时的用户与首个会话合并提交。
- 注销持久化失败时返回 500，不清除浏览器 Cookie，也不声称注销成功。

**回归测试**

- `TestFileStoreMutationRollsBackWhenSaveFails`
- `TestLogoutKeepsCookieWhenSessionDeleteCannotPersist`
- `TestFailedMutationIsNotPersistedByLaterSuccessfulMutation`
- `TestMailboxSyncBatchPersistsMessagesAndCursorsOnce`
- `TestStoreRejectsMailboxForMissingOwnerOrAccount`

**验收标准**

- 故障注入使临时文件写入、关闭或替换失败后，`Snapshot()` 与重启后的状态均保持修改前内容。
- 一个同步批次最多提交一次状态文件。
- 所有现有迁移测试在 Windows 下通过。

### P0-02 管理员初始化、用户开通和鉴权限流

**现状与根因**

`POST /api/auth/register` 完全公开，`CreateUser` 把状态中第一个用户自动设为管理员。公开部署存在管理员抢注窗口，初始化后仍允许无限匿名注册。注册和已知用户名登录在 `FileStore.mu` 内执行 120,000 轮 PBKDF2，且没有限流，攻击请求会阻塞所有 Store 操作。

**修复设计**

- 新增 `POST /api/auth/bootstrap`：
  - 仅当状态中没有用户时可调用。
  - 必须通过 `Authorization: Bearer <IPM_BOOTSTRAP_TOKEN>` 提交一次性启动令牌。
  - 令牌只从环境变量读取，不写入 `config.json`、状态文件、日志或响应。
  - 初始化成功后，即使环境变量仍存在也拒绝再次执行。
- 将 `POST /api/auth/register` 改为兼容性错误响应 `registration_closed`，不再创建用户。
- 新增管理员鉴权接口 `POST /api/admin/users` 创建普通用户；不能通过请求参数创建管理员。
- 登录默认限流：
  - 按规范化用户名和客户端 IP 分别计数。
  - 连续失败 5 次后封禁 15 分钟；成功登录清除该用户名失败计数。
  - bootstrap 与用户创建入口按客户端 IP 每分钟最多 3 次。
  - 状态仅驻留内存，重启后清空，不增加持久化结构。
- 客户端 IP 默认使用 `RemoteAddr`；只有直接对端为 loopback 时才接受代理传入的首个合法 IP，公网直连时忽略伪造的转发头。
- 在短锁内读取用户 ID、状态与密码哈希，解锁后执行 PBKDF2；完成后通过事务式 Store 重新确认用户未被停用且哈希未变化，再更新登录时间并创建会话。
- 未知用户名执行等成本的固定 dummy hash，降低用户名时序枚举。
- 启动状态接口只返回 `needs_bootstrap`，不得泄露启动令牌是否配置。

**回归测试**

- 替换现有 `TestUserLoginScopesDataAndFirstUserIsAdmin`，新增：
  - `TestBootstrapRequiresEmptyStoreAndToken`
  - `TestBootstrapCannotRunTwice`
  - `TestPublicRegistrationIsClosed`
  - `TestAdminCreatesNormalUser`
  - `TestPasswordVerificationDoesNotHoldStoreLock`
  - `TestLoginRateLimitByUsernameAndClientIP`
  - `TestUnknownAndKnownUserLoginHaveEquivalentHashWork`

**验收标准**

- 空状态下没有启动令牌不能产生管理员。
- 已初始化实例不能通过公开端点创建任何用户。
- 并发错误登录期间，健康检查和只读 Store 请求仍可及时完成。

### P0-03 Apple 2FA 流程归属与提交状态机

**现状与根因**

两个 `appleAuthPendingStore` 都是 Server 全局对象；pending 只保存随机 ID、会话指针和时间，不保存发起它的面板用户。任意持有 `pending_id` 的已登录用户都能提交，并把结果保存到自己的 owner。`get` 返回共享可变指针，同一 pending 可并发提交；成功后又先删除 pending，再保存 session，落盘失败会永久丢失已经完成的 2FA 结果。

**修复设计**

- pending 增加 `OwnerID`、流程类型、不可变 Apple 会话快照和状态：`waiting`、`submitting`、`completed`。
- start handler 在创建 pending 时写入当前 `OwnerID`；submit 必须用常量时间比较当前 owner，归属不匹配统一返回与过期相同的错误，避免泄露 pending 是否存在。
- `waiting → submitting` 必须在 pending store 内原子完成；并发提交返回 `409 apple_login_in_progress`。
- Apple 返回可重试错误时恢复为 `waiting`；不可重试错误按现有业务规则保留或删除。
- Apple 成功后先把完成的 `ICloudSession` 保存到 pending 的 `completed` 状态，再通过事务式 Store 持久化到正确 owner；持久化成功后才删除 pending。
- `completed` 状态的重试只重复本地保存，不再次调用 Apple。
- 不向调用者暴露内部 Session 指针；pending store 返回值必须深拷贝或在锁内操作。
- 旧接口和新接口共用同一状态机实现，避免修复只覆盖一条路径。

**回归测试**

- `TestApple2FAPendingRejectsDifferentOwner`
- `TestICloudProtocol2FAPendingRejectsDifferentOwner`
- `TestApple2FAPendingAllowsSingleSubmitter`
- `TestApple2FAKeepsCompletedSessionWhenPersistFails`
- `TestApple2FARetryAfterPersistFailureDoesNotCallAppleAgain`
- 使用 `go test -race` 验证同一 pending 的并发提交。

**验收标准**

- 用户 A 发起的 pending 在用户 B 会话中不可提交。
- 并发提交只产生一次 Apple 请求和一次本地 session 提交。
- 本地保存失败后 pending 仍能恢复完成结果。

### P0-04 邮件收件人精确归属

**现状与根因**

IMAP 路径把全部邮件头拼成 `recipients`，共享 helper 再使用不分字段的子串查找邮箱别名。因此 Subject、From 或任意扩展头提到另一个邮箱时，会把验证码同时写入错误邮箱；互为前缀的别名也可能误匹配。WebService 路径还把 `LongHeader` 整体加入归属文本。

**修复设计**

- IMAP 只解析 `To`、`Cc`、`Bcc` 的结构化地址列表；主题、发件人、正文和任意未明确允许的扩展头不参与归属。
- WebService 直接解析 `to`、`cc`、`bcc` JSON 字段，不把 `LongHeader` 当作自由文本搜索源。
- 使用 `net/mail` 地址解析后规范化地址，并以大小写不敏感的完整地址相等匹配，禁止 `strings.Contains`。
- 一封邮件的结构化收件人确实包含多个受管别名时，允许归属到多个邮箱。
- 解析失败的单个地址记录不含原始敏感头的诊断日志，其余可解析地址继续处理。

**回归测试**

- 扩展 `internal/app/imap_client_test.go`：
  - `TestRecipientMatchingIgnoresAliasInSubject`
  - `TestRecipientMatchingIgnoresAliasInFromAndExtensionHeaders`
  - `TestRecipientMatchingRequiresExactAddress`
  - `TestRecipientMatchingAllowsMultipleActualRecipients`
- WebService 路径增加等价测试，确保两条同步通道使用同一规范化规则。

**验收标准**

- 实际发给 alias-A、但主题包含 alias-B 的邮件只能进入 A。
- `a@icloud.com` 不得匹配 `aa@icloud.com`。

### P0-05 IMAP 积压按最旧未检查邮件连续推进

**现状与根因**

当前实现搜索全部 UID 后排序，只保留最后 `maxMessages` 个，再把账号游标保存为所选集合的最大 UID。例如游标 100、积压 101–110、上限 8 时，只读取 103–110 并保存 110，101/102 永远不会再次出现。后台默认上限仅 8，突发邮件即可触发。

**修复设计**

- 搜索结果排序后只取最前面的 N 个未检查 UID，而不是最后 N 个。
- 客户端再次过滤所有 `uid <= cursor` 的结果，规避 IMAP `UID n:*` 在 `n > *` 时仍可能包含最后一封的范围语义。
- `LastUID` 表示本批次真正完成检查的最后一个 UID，不使用完整搜索结果最大值。
- FETCH 命令整体失败不提交消息、不推进游标。
- 成功读取但与验证码无关、或单封格式损坏的邮件视为已经检查并记录结果，避免永久毒消息；不得记录邮件正文或认证信息。
- 每批消息和对应连续游标通过 P0-01 的批量事务一次提交。
- 当仍有积压时主动唤醒下一轮，但保留已有同步最小间隔，避免忙循环。

**回归测试**

- `TestIMAPBacklogFetchesOldestBatchFirst`
- `TestIMAPCursorStopsAtLastProcessedUID`
- `TestIMAPFetchFailureDoesNotAdvanceCursor`
- `TestIMAPFiltersUIDAtOrBeforeCursor`
- `TestIMAPBacklogEventuallyProcessesEveryUID`

**验收标准**

- 101–110、批量 8 的两轮结果必须依次为 101–108 和 109–110。
- 任意批次中断后允许重复检查，不允许跳过未检查 UID。

### P0-06 验证码查询改为可重复幂等读取

**现状与根因**

当前 `writeMailboxCode` 读取 `LastCodeMessageID` 并跳过已经返回过的邮件，随后调用 `SetMailboxLastCode` 记录“已发放”。该逻辑与已确认的领域语义相反：所有授权请求都应在新鲜窗口内得到同一个最新验证码。

**修复设计**

- 删除查询流程中的 `skipMessageID`、`latestMailboxCodeSkipping` 和 `SetMailboxLastCode` 写入。
- 从 `Mailbox` 模型移除 `LastCodeMessageID`、`LastCodeAt`；旧 JSON 字段由解码器忽略，并在下一次成功保存时自然消失。
- `peek=1` 作为兼容参数保留一个发布周期，但变成无副作用的 no-op；响应可增加弃用提示，随后再决定是否删除。
- `cache=1` 仍表示只查本地缓存，不触发同步，但返回规则与普通查询一致。
- 面板和外部 API 都使用同一“最新、关键词匹配、五分钟新鲜窗口”选择函数。

**回归测试**

- 将 `TestMailboxCodeQueryDoesNotRepeatServedCachedCode` 改为 `TestMailboxCodeQueryRepeatsFreshCachedCode`。
- 将 `TestMailboxCodePeekDoesNotConsumeServedCode` 改为断言 `peek` 与普通查询结果一致且都不写状态。
- `TestConcurrentMailboxCodeQueriesReturnSameFreshCode`
- `TestMailboxCodeQueryStopsReturningCodeAfterFreshWindow`

**验收标准**

- 同一有效验证码可被顺序和并发请求重复读取。
- 取码请求不触发状态文件写入。

### P0-07 严格 JSON 请求边界

**现状与根因**

`decodeJSON` 只执行一次 `Decode`，因此合法对象后的第二个 JSON 值会被忽略；当前 1 MiB `LimitReader` 也没有独立、清晰的超限错误。

**修复设计**

- 第一次 Decode 成功后再 Decode 一次，只有 `io.EOF` 才接受；第二个值或非空垃圾统一返回 `bad_json`。
- 允许尾随空白。
- 明确区分 `request_too_large` 与语法错误，响应不回显完整请求内容。
- 保留 `DisallowUnknownFields`。
- 所有 JSON handler 继续共用这一入口，避免逐路由补丁。

**回归测试**

- `TestDecodeJSONRejectsTrailingValue`
- `TestDecodeJSONRejectsTrailingGarbage`
- `TestDecodeJSONAllowsTrailingWhitespace`
- `TestDecodeJSONRejectsBodyOverLimit`

**验收标准**

- `{"value":1}{"value":2}` 必须返回 400。
- 超过限制的请求不进入业务 handler。

## 7. P1：生命周期、恢复与资源安全

### P1-01 绑定 UIDVALIDITY 并修正 UID 范围边界

**修复设计**

- 从 `SELECT INBOX` 响应解析并持久化 `UIDVALIDITY`，模型字段命名为 `IMAPUIDValidity`。
- 每次同步先比较服务器值与保存值；一致才使用 UID 游标。
- 不一致或旧状态没有 UIDVALIDITY 时，清除账号和邮箱 UID 游标，按 `mail_watcher_lookback_hours` 回看，默认 24 小时。
- 回扫仍依赖远端消息标识去重。
- 对 `UID cursor+1:*` 返回值做客户端下界过滤，服务器没有新邮件时游标不得倒退或重复写盘。

**测试与验收**

- `TestIMAPSelectParsesUIDValidity`
- `TestIMAPUIDValidityChangeResetsCursorAndUsesLookback`
- `TestIMAPEmptyRangeDoesNotMoveCursorBackward`
- 世代变化后可补回 24 小时内邮件，且不会重复插入已有 RemoteID。

### P1-02 防止陈旧整会话覆盖新状态

**现状与根因**

keepalive 读取整个 session 快照，网络调用期间同步可能更新 IMAP 游标；keepalive 随后保存旧 session，`mergeLoginStates` 按 Kind 整体替换，导致新游标倒退。

**修复设计**

- 网络操作只返回它负责的 AppleAccount 登录态变更。
- Store 提供按 `owner + account + LoginState.Kind` 的定向更新，在提交时读取最新状态，只覆盖该 kind 的字段。
- Apple keepalive 不得写入 ICloudIMAP 状态；IMAP 同步也不得覆盖 AppleAccount 或 ICloudWeb 状态。
- 删除用户或账号后，定向更新返回 not found，不能重新创建 owner/session。

**测试与验收**

- `TestKeepAliveDoesNotOverwriteNewerIMAPCursor`
- `TestLoginStateUpdateOnlyTouchesRequestedKind`
- `TestStaleSessionSaveCannotRecreateDeletedOwner`

### P1-03 App 专用密码更新必须重启 IDLE worker

**修复设计**

- watcher 分组签名增加不会泄露明文的凭据指纹，例如 App 密码 SHA-256；指纹只用于内存比较，不进入日志或响应。
- 保存新 App 密码后主动 wake watcher。
- 签名变化时取消并等待旧 worker，随后用最新状态启动新连接。
- 邮箱同步游标仍不进入签名，避免每次同步无意义重连。

**测试与验收**

- `TestMailWatcherSignatureChangesWithIMAPCredential`
- `TestMailWatcherRestartsWorkerAfterAppPasswordChange`
- `TestMailWatcherSignatureStillIgnoresSyncCursor`

### P1-04 用户关闭、后台任务和进程退出

**修复设计**

- 增加按 owner 的运行时生命周期门：普通操作获取共享 lease；删除获取独占 drain 权限，阻止新操作并等待已有 lease 释放。
- 删除开始后取消该 owner 的 scheduler、同步、创建和保活上下文。
- 最多等待 30 秒；超时释放删除门并返回 `409 user_busy`，不提交用户删除。
- 所有后台写入在提交前再次验证 owner 和 account 存在。
- scheduler 不再基于裸 `context.Background()`；由 Server 根 context 派生，并纳入统一 WaitGroup。
- 主程序关闭顺序：停止接收新请求、取消 Server 根 context、等待 scheduler/watcher/keepalive、最后关闭 HTTP server；总超时沿用 10 秒时需在日志中明确未完成任务。

**测试与验收**

- `TestDeleteUserWaitsForOwnerJobsBeforeCommit`
- `TestDeleteUserReturnsConflictWhenOwnerJobDoesNotStop`
- `TestBackgroundWriteCannotRecreateDeletedOwner`
- `TestServerShutdownCancelsAndWaitsForSchedulers`

### P1-05 在线更新资产完整性

**修复设计**

- 自定义 manifest 中匹配资产的 SHA-256 为空或格式非法时，`AssetAvailable` 可为 true，但 `ApplyAvailable` 必须为 false。
- GitHub Release 查找与目标二进制同名的 `.sha256` 或统一 checksums 文件，严格解析当前资产的 64 位十六进制摘要。
- 下载后必须常量时间比较摘要；不匹配时删除临时文件，保留原可执行文件。
- Windows 继续返回 `update_unsupported`，不改变手工更新流程。
- 更新状态响应明确区分“有新版”“有适配资产”“可安全一键更新”。

**测试与验收**

- `TestManifestUpdateRequiresSHA256`
- `TestGitHubReleaseLoadsMatchingChecksum`
- `TestUpdateRejectsMissingOrMismatchedChecksum`
- 没有 checksum 的发布只能提示，不能进入替换函数。

### P1-06 Hashcash 取消与高难度尾部失败

**现状与根因**

24-bit challenge 最多尝试 `2^24` 次，合法挑战仍有约 36.8% 概率在上限内找不到解；计算循环不检查 Context。

**修复设计**

- `generateAppleHashcash` 接收 Context，不再以 `2^24` 次作为成功与否边界。
- 保留最大难度 24 bit；循环每固定小批次数检查 `ctx.Err()`，由现有请求超时限定总 CPU 时间。
- 超时返回明确可重试错误，不把“未在平均工作量内找到解”误报为挑战非法。
- 日志仅记录 bits、耗时和取消原因，不记录 challenge 或生成结果。

**测试与验收**

- 保留现有 8-bit 正确性测试。
- 新增 `TestGenerateAppleHashcashHonorsCancellation` 和边界计数测试。
- 取消请求后计算必须在短时间内退出。

### P1-07 WebSession 过期清理

**修复设计**

- 启动加载状态时清理过期会话并通过事务式提交保存。
- 创建或删除会话时再次顺带清理过期项。
- 普通 `WebSessionByToken` 保持只读，不因每次请求触发磁盘写入。
- 管理状态接口可返回会话总数和过期清理计数，但不得返回 token hash。

**测试与验收**

- `TestStorePrunesExpiredWebSessionsOnLoadAndCreate`
- 当前有效会话不受迁移影响；过期项在一次启动或新登录后消失。

### P1-08 并行 IMAP 拨号连接回收

**修复设计**

- 首个连接成功后取消其他拨号。
- worker 在发送结果前发现 context 已取消时主动关闭成功连接。
- 接收方确保所有已经进入结果通道但未采用的连接最终关闭。
- 为拨号函数增加最小测试注入点，不引入新的网络抽象层。

**测试与验收**

- `TestIMAPParallelDialClosesLosingSuccessfulConnections`
- 成功、失败和取消路径的假连接 Close 次数均可断言。

## 8. P2：前端与部署行为

### P2-01 删除末页数据后的分页收敛

**修复设计**

- 后端过滤完成后计算 `total_pages`；总数为 0 时实际页固定为 1，否则把请求页钳制到 `[1, total_pages]`，再切片。
- 响应中的 `pagination.page` 必须是实际返回页。
- 前端每次刷新用响应页覆盖本地 `mailboxPage`。
- 删除最后一页唯一记录后自动显示新的最后一页。

**测试与验收**

- `TestMailboxListClampsPageAfterLastItemDeleted`
- 10 条数据请求 `page=2&page_size=10` 返回 page 1 和 10 条记录。

### P2-02 前端异步操作必须呈现失败并防重复

**修复设计**

- 新旧 Apple 登录 start 函数增加 `try/catch/finally`：请求期间禁用对应按钮，失败时更新状态文本与日志，结束后恢复按钮。
- 2FA、scheduler 启停、邮箱删除/状态修改等直接异步操作应用相同行为。
- 同一按钮只允许一个进行中的 Promise；不增加全局任务框架。
- 错误文本使用 API 的稳定 message/code，不显示堆栈、密码或响应原文。

**测试与验收**

- Node VM 中 mock `api()` rejected Promise，断言错误可见、按钮恢复且快速双击只发一个请求。
- 三个 HTML 模板内联 JavaScript 继续通过语法编译。

### P2-03 面板同源取码与公开 URL 生成

**修复设计**

- 登录面板调用 `/api/mailboxes/{id}/code` 相对路径，不使用 `row.api_url`。
- `authorized` 增加 Web Session 分支，并调用现有邮箱 owner 校验；外部邮箱 token 与全局 API Key 行为保持不变。
- 不配置 `public_base_url` 时，公开 API URL 返回相对路径，不从不可信 Host 头拼接绝对地址。
- 配置 `public_base_url` 时继续生成外部绝对 URL；启动时校验其 scheme 和 host。
- `X-Forwarded-Proto` 不再影响面板取码；其他确需绝对 URL 的位置只在直接对端为可信本地代理时使用转发协议。

**测试与验收**

- `TestPanelMailboxCodeUsesWebSessionAndOwnerScope`
- `TestPanelMailboxCodeURLIsSameOrigin`
- `TestMailboxAPIURLUsesConfiguredPublicBaseURLOrRelativePath`
- HTTPS 页面不产生 HTTP 请求，不需要 CORS。

## 9. 数据与配置迁移

### 9.1 状态文件

发布前复制 `data/state.json` 为带时间戳备份。升级加载规则：

- 已存在任意用户：视为已经完成管理员初始化，不要求也不接受 bootstrap。
- `LastCodeMessageID`、`LastCodeAt`：加载时忽略，下一次成功保存自然删除；不会影响验证码查询。
- 新增 `IMAPUIDValidity`：旧状态为 0，首次同步按 UIDVALIDITY 未知处理，回看最近 24 小时并去重。
- 过期 WebSession：启动时清理；有效 Cookie 保持有效。
- Apple pending：仅在内存中存在，升级重启后仍按现有行为要求重新发起登录。

任何迁移失败都必须保持原文件和内存未变，并阻止服务进入可写状态。

### 9.2 配置

- 新增环境变量 `IPM_BOOTSTRAP_TOKEN`，只在空状态初始化时使用。
- 不为限流参数增加配置项；先使用已确认默认值，出现真实运营需求再开放。
- 复用现有 `mail_watcher_lookback_hours`，默认 24。
- `public_base_url` 继续可选；缺省时外部 URL 使用相对路径。
- 不新增 Go module 依赖。

## 10. 可观测性与敏感信息

- 新增稳定日志事件：`auth_rate_limited`、`bootstrap_completed`、`imap_cursor_reset`、`imap_backlog_remaining`、`owner_drain_timeout`、`update_checksum_missing`。
- 日志消息保持英文，字段可包含 owner/account/mailbox ID、UIDVALIDITY、批次数量和耗时。
- 禁止记录：密码、App 专用密码、Cookie、session token、pending ID、验证码、完整邮件头/正文、Hashcash challenge。
- Store 提交失败日志包含阶段（encode/write/sync/rename）和路径类别，不打印状态内容。
- 指标至少覆盖同步批次 UID 范围、积压数、Store 提交耗时/字节数、限流命中和后台任务停止耗时。

## 11. 发布与回滚

### 11.1 P0 发布

1. 备份状态文件。
2. 先上线事务式 Store 和批量提交。
3. 再上线 bootstrap/管理员用户创建、2FA owner 绑定、邮件归属、连续游标、幂等取码和严格 JSON。
4. 观察一个完整邮件高峰周期，确认无游标跳跃、跨邮箱写入或 Store 提交错误。

回滚：停止服务，恢复 P0 发布前状态备份，再启动旧版本。不要让旧版本读取已经部分失败的临时文件。

### 11.2 P1 发布

1. 再次备份状态。
2. 上线 UIDVALIDITY 后首次同步会产生有界回扫，发布窗口应允许额外 IMAP 流量。
3. 验证 App 密码更新、keepalive 并发、用户删除和 SIGTERM 关闭。
4. 在线更新只有 checksum 可用时才做端到端演练。

回滚：新增 JSON 字段对旧版本保持可忽略；恢复备份可避免旧版使用 P1 已重置的游标。

### 11.3 P2 发布

P2 不迁移状态；可直接回滚静态模板和 handler 行为。回滚前确认外部 token API 未被改变。

## 13. 建议的实现切片

每个切片保持可独立审查和回滚：

1. `fix(store): commit state mutations transactionally`
