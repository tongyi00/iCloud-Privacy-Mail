## 1. 目标

修复 P0、P1、P2 完成后代码审查确认的两个遗留问题：

1. `public_base_url` 接受 query、fragment 或用户信息，随后通过字符串拼接生成语义错误或包含敏感信息的外部验证码 API URL。
2. 内存认证限流器只新增键，不回收已过期的用户名、IP 和操作限流项，长期运行时 `entries` 会持续增长。

完成后必须保持以下既有行为：

- 验证码查询仍是幂等读取；同一有效验证码可以被多次返回。
- 面板验证码查询仍使用同源相对地址和 Web Session owner 鉴权。
- 外部验证码 API 仍兼容邮箱 token 与全局 API Key。
- `public_base_url` 仍为可选配置，并允许合法的反向代理路径前缀。
- 登录失败阈值、封禁时长、bootstrap 和管理员创建用户的限流阈值均不变化。
- 限流状态仍只保存在内存中，服务重启后清空。

## 4. F-01：严格限定 `public_base_url`

### 4.1 当前行为

`internal/app/config.go` 的 `validateConfig` 当前只验证：

- `url.Parse` 成功；
- `Host` 非空；
- scheme 为 `http` 或 `https`。

`internal/app/server.go` 的 `mailboxAPIURL` 随后执行：

```go
return baseURL + path
```

因此配置值中的 query 或 fragment 会改变后续拼接内容的 URL 语义。

已稳定复现：

| 配置值 | 当前结果 |
| --- | --- |
| `https://public.example/base?x=1` | 被接受，API 路径进入 query 值 |
| `https://public.example/base#fragment` | 被接受，API 路径进入 fragment，不会发送到服务器 |
| `https://user:password@public.example/base` | 被接受，导出的公开 URL 包含用户信息 |

### 4.2 目标不变量

`public_base_url` 只表示外部服务的 HTTP(S) origin 和可选路径前缀，不得包含：

- 用户信息；
- query，包括空 query 分隔符 `?`；
- fragment，包括空 fragment 分隔符 `#`。

空配置继续表示“生成相对外部 API URL”。合法路径前缀继续保留。

### 4.3 输入规则

| 输入 | 预期 |
| --- | --- |
| 空字符串或纯空白 | 接受并规范化为空字符串 |
| `https://public.example` | 接受 |
| `http://127.0.0.1:8787` | 接受 |
| `https://public.example/base` | 接受并保留 `/base` |
| `https://public.example/base/` | 接受并去掉末尾 `/` |
| `//public.example/base` | 拒绝：缺少 scheme |
| `ftp://public.example/base` | 拒绝：scheme 非 HTTP(S) |
| `https:///base` | 拒绝：缺少 host |
| `https://user@public.example/base` | 拒绝：包含用户信息 |
| `https://public.example/base?x=1` | 拒绝：包含 query |
| `https://public.example/base?` | 拒绝：包含空 query 分隔符 |
| `https://public.example/base#x` | 拒绝：包含 fragment |
| `https://public.example/base#` | 拒绝：包含空 fragment 分隔符 |
| `https://public.example/base%3Fx` | 接受：`?` 是路径中的编码字符 |

URI scheme 按标准进行大小写无关比较。除此之外不主动重写 host、端口或路径，避免改变部署者配置的路径语义。

### 4.4 最小实现

修改 `internal/app/config.go` 的 `validateConfig`，继续使用标准库 `net/url`，在同一信任边界完成全部校验。

推荐判定条件：

```go
parsed, err := url.Parse(value)
validScheme := strings.EqualFold(parsed.Scheme, "http") || strings.EqualFold(parsed.Scheme, "https")
if err != nil || !parsed.IsAbs() || parsed.Host == "" || !validScheme ||
	parsed.User != nil || strings.ContainsAny(value, "?#") {
	return Config{}, errors.New("public_base_url must be an absolute http or https URL without user info, query, or fragment")
}
```

说明：

- `strings.ContainsAny(value, "?#")` 用于覆盖 `RawQuery`、`Fragment` 为空但分隔符仍存在的情况。
- 编码后的 `%3F`、`%23` 不会被误拒绝。
- 继续在校验前执行 `TrimSpace` 和 `TrimRight(..., "/")`。
- `mailboxAPIURL` 不需要改成新的 URL 构建抽象；配置不变量建立后，现有 `baseURL + path` 对允许的输入是确定的。
- 不在 `mailboxAPIURL` 重复校验。所有 `LoadConfig` 成功出口已经汇入 `validateConfig`，修复一次即可覆盖文件、环境变量和缺失配置文件三条路径。

## 5. F-02：回收过期认证限流项

### 5.1 当前行为

`authRateLimiter.entries` 同时保存：

- `login-user:<username>`；
- `login-ip:<ip>`；
- `bootstrap:<ip>`；
- `create-user:<ip>`。

当前方法只会覆盖同名键；`recordLoginSuccess` 只删除成功用户名对应的键。窗口过期后，旧键仍永久留在 map 中。

已稳定复现：创建 100 个已经超过窗口的不同键，再触发一个新窗口操作，map 仍保留 101 项。

### 5.2 目标不变量

- 每个限流项必须具有明确的内存到期时间。
- 到期项在后续认证操作中机会式清理，不需要后台任务。
- 清理与限流判断在现有 mutex 下完成，不引入数据竞争。
- 活跃封禁项不能因为窗口清理而提前消失。
- 阈值边界和错误响应保持不变。

### 5.3 生命周期定义

| 项类型 | 到期时间 |
| --- | --- |
| 登录用户名/IP，未封禁 | `windowStart + authBlockDuration` |
| 登录用户名/IP，已封禁 | `max(windowStart + authBlockDuration, blockedUntil)` |
| bootstrap/创建用户操作 | `windowStart + authActionWindow` |

成功登录继续立即删除 `login-user:<username>`。IP 失败记录仍保留到自然到期，避免一个账号登录成功清除共享 IP 的整体防爆破状态。

### 5.4 最小数据结构调整

在 `internal/app/server.go` 中扩展现有类型：

```go
type authRateEntry struct {
	count        int
	windowStart  time.Time
	blockedUntil time.Time
	expiresAt    time.Time
}

type authRateLimiter struct {
	mu            sync.Mutex
	entries       map[string]authRateEntry
	lastCleanupAt time.Time
}
```

新增常量：

```go
const authRateCleanupInterval = time.Minute
```

不增加配置项。清理间隔只影响过期对象最多额外保留多久，不影响用户可见限流语义。

### 5.5 锁内清理函数

新增一个未导出的锁内 helper：

```go
func (l *authRateLimiter) cleanupExpiredLocked(now time.Time) {
	elapsed := now.Sub(l.lastCleanupAt)
	if !l.lastCleanupAt.IsZero() && elapsed >= 0 && elapsed < authRateCleanupInterval {
		return
	}
	for key, entry := range l.entries {
		if entry.expiresAt.IsZero() || !entry.expiresAt.After(now) {
			delete(l.entries, key)
		}
	}
	l.lastCleanupAt = now
}
```

约束：

- 只能在持有 `l.mu` 时调用，名称保留 `Locked` 后缀。
- 时钟向后跳变时不应永久跳过清理；`elapsed < 0` 时允许执行一次清理。
- `expiresAt` 为零的项视为不可继续使用并删除。限流状态不持久化，因此不存在升级迁移问题。
- 清理最多每分钟全表扫描一次，避免每个登录请求都执行 O(n) 遍历。

### 5.6 修改现有方法

四个入口在获取 mutex 后首先调用 `cleanupExpiredLocked(now)`：

- `loginBlocked`；
- `recordLoginFailure`；
- `recordLoginSuccess`；
- `allowAction`。

为保持测试使用显式时钟，将 `recordLoginSuccess` 签名改为：

```go
func (l *authRateLimiter) recordLoginSuccess(username string, now time.Time)
```

其唯一调用点 `handleAuthLogin` 传入 `time.Now()`。不要在 helper 内部再次读取系统时间，避免同一次判断使用两个时间基准。

`recordLoginFailure` 在更新计数和 `blockedUntil` 后设置：

```go
entry.expiresAt = entry.windowStart.Add(authBlockDuration)
if entry.blockedUntil.After(entry.expiresAt) {
	entry.expiresAt = entry.blockedUntil
}
```

`allowAction` 在建立或复用窗口后设置：

```go
entry.expiresAt = entry.windowStart.Add(authActionWindow)
```

不要修改下列行为：

- 第 5 次登录失败触发 15 分钟封禁；
- bootstrap 和管理员创建用户在同一窗口内第 4 次请求被拒绝；
- `loginBlocked` 只查询，不创建新键；
- 登录成功只清理用户名键，不清理 IP 键。

### 5.7 为什么不增加后台清理线程或第三方库

认证请求本身就是限流状态的唯一读写入口，机会式清理能够结束长期泄漏。后台线程会增加关闭顺序、定时器和测试复杂度，第三方依赖也不能改善当前单进程需求。

本修复解决“过期项永久保留”。它不是边缘 DDoS 防护：一分钟内出现海量真实来源 IP 时，仍应由反向代理设置连接数、请求速率和请求体限制。本次不为尚未出现的容量需求引入 LRU 或分布式存储。

### 5.8 回归测试

修改 `internal/app/p0_regression_test.go`，使用显式 `time.Time` 推进时钟，不使用 `time.Sleep`。

   - 让登录项达到封禁阈值；

   - 窗口到期后再次允许。
4. `TestAuthRateLimiterCleanupHandlesClockRollback`
   - 将 `lastCleanupAt` 设为晚于当前 `now`；

### 5.9 验收标准

- 过期登录和操作键会在下一次符合清理间隔的认证操作中删除。
- 活跃封禁不会提前解除。
- 所有现有限流回归测试保持通过。
- `go test -race` 环境可用时不报告 `authRateLimiter` 数据竞争。
- 不新增 goroutine、依赖、持久化字段或配置项。

### 8.1 数据和配置

- 不修改 `state.json` 结构，不需要备份或迁移脚本。

### 8.3 回滚

代码回滚不涉及数据降级。若发布后发现合法部署 URL 被误拒绝：

1. 保留失败配置与启动错误日志；
2. 回滚修复提交；
3. 将该 URL 作为新的失败测试分析；
4. 不通过放宽到任意 query/fragment 来临时绕过。
